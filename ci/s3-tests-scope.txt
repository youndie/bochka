deferred	object_read_unreadable	the premise of the original task was wrong and that was the finding: the key arrives as %C2%AE%C2%8A-, which is well-formed UTF-8, so this is not a malformed key but a key holding C1 control characters, and S3 refuses it at the URI with "Couldn't parse the specified URI." Refusing those here contradicts a documented decision (Р2: keys are not restricted, and encoding-type=url exists because a listing must carry bytes XML cannot). Settled by a source that says which bytes are invalid in a request line, not by one case
deferred	unicode_metadata	measured rather than guessed, and the earlier reason here was wrong: botocore does send non-ASCII metadata, as UTF-8, and reads the response back as latin-1. Passing this case means decoding the value as UTF-8 on the way in and re-encoding it as latin-1 on the way out, which makes metadata lossy above U+00FF — today it round-trips byte for byte. Settled by a source on what S3 stores, not by one case that only pins the asymmetry of one client
