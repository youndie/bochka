# Развёртывание

Одна машина, один диск, nginx впереди. Больше bochka ничего не умеет, и это записано в `README`
как ниша, а не как ограничение, которое когда-нибудь снимут.

## Почему TLS снаружи, а не внутри

Не из удобства и не «пока не дошли руки» — из §1.7 ресёрча. Терминировать TLS внутри JVM без
потери zero-copy нельзя: kTLS нужны секреты сессии, а JSSE их не отдаёт наружу вообще. Отсутствует
не системный вызов, а доступ к ключам. Значит, сервер на Java, говорящий TLS, шифрует каждый байт
в пользовательском пространстве — то есть отменяет ровно то свойство, ради которого устроен весь
путь чтения (**5.3× процессора на байт**, [docs/measurements.md](../docs/measurements.md)).

У nginx этой проблемы нет: он отдаёт ключи ядру и `sendfile` работает **сквозь** TLS. Быстрый путь
сохраняется переносом TLS, а не отказом от него.

Побочно это единственный способ увидеть четвёртый способ передачи тела: `aws-cli` шлёт
`STREAMING-UNSIGNED-PAYLOAD-TRAILER` только поверх TLS. Без терминатора его не проверяет ничто —
поэтому он есть и в [`ci/live-clients.sh`](../ci/live-clients.sh).

## Что запустить

```bash
docker run -d --name bochka \
  -u 1000:1000 \
  -v /srv/bochka:/var/lib/bochka \
  -p 127.0.0.1:9000:9000 \
  -e BOCHKA_KEYS='youraccesskey:yoursecretkey' \
  ghcr.io/youndie/bochka:latest

docker run -d --name bochka-tls --network host \
  -v $PWD/deploy/nginx/nginx.conf:/etc/nginx/nginx.conf:ro \
  -v /etc/letsencrypt/live/example.com:/etc/nginx/tls:ro \
  nginx:alpine
```

`-p 127.0.0.1:9000:9000`, а не `-p 9000:9000`: хранилище, доступное из сети без TLS впереди, —
это хранилище, чьи подписи ездят открытым текстом.

`-u 1000:1000` — образ создаёт пользователя именно с этим номером, потому что 1000 это первый id,
который Linux выдаёт человеку, и значит id, которому принадлежит примонтированный каталог на
чьей-то машине. Каталог с другим владельцем придётся `chown` вручную; проверяется это
в [`ci/docker-smoke.sh`](../ci/docker-smoke.sh).

## Настройки

Их список — единственный, и он живёт в
[`Configuration.Key`](../bochka-app/src/main/kotlin/io/github/youndie/bochka/app/Configuration.kt).
Имя пишется `data.dir` в файле (`BOCHKA_CONFIG`) и `BOCHKA_DATA_DIR` в окружении; окружение
выигрывает.

**Неизвестное имя останавливает процесс.** `BOCHKA_DATADIR` вместо `BOCHKA_DATA_DIR` — это объекты
во временном каталоге и сервер, который об этом молчит; поэтому он не молчит, а отказывается
стартовать, называет опечатку и подсказывает ближайшее настоящее имя. Цена честная и стоит того,
чтобы её назвать: переменная `BOCHKA_*`, заведённая в окружении для чего-то другого, этот сервер
остановит.

## Сколько объектов поместится

Столько, сколько поместится в кучу: индекс держит все ключи (Р1). Умолчание поставки — `-Xmx512M`,
то есть около **413 000 объектов** при 650 байтах индекса на объект. Больше — больше куча:

```bash
-e JAVA_TOOL_OPTIONS=  # нет; профиль рантайма перебивать нельзя
```

Профиль задаётся при сборке дистрибутива и **не** берётся из `JAVA_OPTS` — иначе базовый образ или
оркестратор молча заменит кучу, от которой выведен объявленный потолок, и опубликованное число
станет числом про процесс, которого никто не запускает. Это проверяется смоук-тестом. Чтобы
поднять потолок, пересоберите дистрибутив с `-Pbochka.jvmArgs`.

Переполнение — **отказ при старте**, а не деградация в своп: процесс, который поднялся и начал
свопиться, выглядит как медленный диск для всех, кто не писал индекс.

## Обслуживание

Раз в час (`BOCHKA_HOUSEKEEPING_MINUTES`) сервер уплотняет журнал индекса, собирает файлы-сироты
и забывает брошенные многочастные загрузки. Уплотнение — не про место на диске: восстановление
пропорционально журналу, и полмиллиона объектов в трёх поколениях открываются 3.5 с против 0.76 с
после уплотнения.

## Проверка здоровья

```
curl -sf -o /dev/null -w '%{http_code}' http://127.0.0.1:9000/   # ждём 403
```

Именно запрос, а не открытие сокета: TCP-соединение устанавливается и с JVM, которая застряла
в сборке мусора и не отвечает ничего. `403` здесь — правильный ответ: запрос без учётных данных
корректен и просто ничей.
