# Развёртывание

Одна машина, один диск, nginx впереди. Больше bochka ничего не умеет, и это записано в `README`
как ниша, а не как ограничение, которое когда-нибудь снимут.

## Почему TLS снаружи, а не внутри

Не из удобства и не «пока не дошли руки» — из §1.7 ресёрча. Терминировать TLS внутри JVM без
потери zero-copy нельзя: kTLS нужны секреты сессии, а JSSE их не отдаёт наружу вообще. Отсутствует
не системный вызов, а доступ к ключам. Значит, сервер на Java, говорящий TLS, шифрует каждый байт
в пользовательском пространстве — то есть отменяет ровно то свойство, ради которого устроен весь
путь чтения (**5.3× процессора на байт**, [docs/measurements.md](../docs/measurements.md)).

У nginx этой проблемы нет: он отдаёт ключи ядру, и шифрование происходит там, а не в его
адресном пространстве.

**Но быстрый путь эта схема не сохраняет, и это стоит знать до того, как считать полосу.**
`sendfile` сквозь TLS работает, когда nginx отдаёт **файл**; здесь он проксирует, файла у него нет,
и `SSL_sendfile` к телу ответа неприменим. Замерено на стенде из двух машин
([docs/measurements.md](../docs/measurements.md)): тот же TLS, тот же kTLS, те же байты стоят
**0.898 с процессора на ГиБ, когда файл есть, и 2.408, когда nginx пересылает сокет**. Сам kTLS
включается и экономит 15 %, а не разы.

Что вынос TLS действительно даёт: путь чтения bochka остаётся нетронутым — **0.27–0.30 с/ГиБ
против 2.4 у nginx**, — а шифрование достаётся процессу, который для него построен. Внутри JVM
пришлось бы платить и за шифрование, и за потерю быстрого пути (7.6× на настоящей сетевой карте),
и за проход каждого байта через кучу.

**Практическое следствие:** проксирующая цепочка с TLS упирается в процессор раньше, чем в сеть.
На четырёх ядрах это около **0.41 ГиБ/с** при линке, который держит 0.86.

## Если этой полосы не хватает

Есть один ключ, который возвращает быстрый путь, и у него названная цена.

`BOCHKA_ACCEL_REDIRECT=/bochka-data` заставляет bochka отвечать на чтение целого объекта
заголовком `X-Accel-Redirect` и пустым телом: файл отдаёт nginx, тем же путём, каким отдаёт
статику. Замерено: **0.947 с процессора на ГиБ против 2.703, то есть 2.85× назад**, и цепочка
снова упирается в сеть (0.76 ГиБ/с), а не в процессор. Сама bochka при этом тратит 0.021 с/ГиБ —
она отвечает заголовками и байтов не касается.

```nginx
location /bochka-data/ {
    internal;                 # снаружи не запросить — только по X-Accel-Redirect
    alias /srv/bochka/data/;  # тот же каталог, что BOCHKA_DATA_DIR, плюс /data
    etag off;
    add_header ETag          $upstream_http_etag          always;
    add_header Last-Modified $upstream_http_last_modified always;
}
```

**Чем платите, по порядку убывания неприятности:**

1. **`Content-Type` в ответе будет неверным или задвоенным.** nginx строит ответ из внутреннего
   location, где имя файла — UUID, и ставит `application/octet-stream`. Вернуть свой можно только
   ещё одним `add_header`, а он **добавляет**, а не заменяет: клиент получит два заголовка.
   Лечится сборкой nginx с `headers-more` (`more_set_headers`), в пакетном его нет. Пока этого
   не сделано, ключ включать не стоит там, где клиенты читают тип;
2. **nginx получает доступ на чтение к каталогу данных** — он перестаёт быть процессом, который
   только терминирует TLS;
3. **обе стороны обязаны жить на одной файловой системе**, то есть терминатор нельзя унести
   на другой хост;
4. **`partNumber` так не отдаётся** — заголовок называет файл и не умеет назвать его кусок;
   такие чтения остаются на bochka и работают как раньше;
5. bochka перестаёт видеть, как байты уходят: журнал доставки — теперь nginx'а.

Без ключа всё работает как прежде, и это умолчание.

Побочно это единственный способ увидеть четвёртый способ передачи тела: `aws-cli` шлёт
`STREAMING-UNSIGNED-PAYLOAD-TRAILER` только поверх TLS. Без терминатора его не проверяет ничто —
поэтому он есть и в [`ci/live-clients.sh`](../ci/live-clients.sh).

## Что запустить

```bash
docker run -d --name bochka \
  -u 1000:1000 \
  -v /srv/bochka:/var/lib/bochka \
  -p 127.0.0.1:9000:9000 \
  -e BOCHKA_KEYS='youraccesskey:yoursecretkey' \
  ghcr.io/youndie/bochka:latest

docker run -d --name bochka-tls --network host \
  -v $PWD/deploy/nginx/nginx.conf:/etc/nginx/nginx.conf:ro \
  -v /etc/letsencrypt/live/example.com:/etc/nginx/tls:ro \
  nginx:alpine
```

`-p 127.0.0.1:9000:9000`, а не `-p 9000:9000`: хранилище, доступное из сети без TLS впереди, —
это хранилище, чьи подписи ездят открытым текстом.

`-u 1000:1000` — образ создаёт пользователя именно с этим номером, потому что 1000 это первый id,
который Linux выдаёт человеку, и значит id, которому принадлежит примонтированный каталог на
чьей-то машине. Каталог с другим владельцем придётся `chown` вручную; проверяется это
в [`ci/docker-smoke.sh`](../ci/docker-smoke.sh).

## В Kubernetes

[`helm/bochka`](helm/bochka) — тот же один процесс и тот же один диск, только описанные так, чтобы
оркестратор не сделал из них двух писателей. Оркестратор к этому склонен: его обычный ответ на
неотвечающий под — поднять ещё один, а каталог данных здесь не защищён ничем, кроме внутрипроцессной
блокировки. Поэтому почти всё, что чарт делает, — это запреты, и почти каждый выведен из строчки
кода, а не из привычки.

```bash
helm install bochka deploy/helm/bochka \
  --set auth.keys[0].id=youraccesskey \
  --set auth.keys[0].secret=yoursecretkey
```

**Обязательны только ключи, и умолчания у них нет намеренно.** Пустой `BOCHKA_KEYS` — это не «без
аутентификации», это две встроенные пары, опубликованные в этом репозитории, и лог называет такой
старт нормальным. Чарт, у которого есть путь, заканчивающийся там, — это чарт, ставящий публичное
хранилище; поэтому без ключей он не рендерится вовсе.

Второе, что стоит задать осознанно, — `region`: подпись сравнивается на точное совпадение, и клиент,
подписавший другой регион, получает `AuthorizationHeaderMalformed`, что читается как проблема
с ключами. Умолчание `us-east-1` — то же, что у сервера и у всех SDK.

Что решено внутри и почему — в [README чарта](helm/bochka/README.md); чего он не обещает — там же
отдельным разделом, и это стоит прочитать раньше установки, а не после.

**Ключи, не попадающие в git.** Форм три, и они не равны:

* `--set` при установке. В репозиторий не попадает — но попадает **в запись релиза**, открытым
  текстом: `helm get values` печатает переданные значения, `helm get manifest` — готовый `Secret`.
  Ревизий по умолчанию хранится десять, поэтому ротация старый ключ не убирает;
* values-файл, живущий вне гита (`-f`), — ровно с тем же следствием;
* `auth.existingSecret` — ссылка на `Secret`, который завёл кто-то другой: внешний менеджер
  секретов, `kubectl create secret`, что угодно. Единственная форма, при которой значение
  не оказывается в записи релиза. Чарт в этот `Secret` не заглядывает, поэтому проверить, что там
  не пусто, он не может при рендере, — это делает `helm test` отрицательной проверкой: подписанный
  запрос встроенной парой `bochkaadmin:bochkasecret` обязан получить отказ.

**И при любой из трёх секрет уезжает в `kubectl logs`.** Сервер печатает свою конфигурацию при
старте, и `keys` печатается вербатим — значит, на первой же строке каждого запуска значение
оказывается в сборщике логов. `Secret` — это место, где значение **хранится**, а не место, где оно
остаётся. Правится это в сервере (заведено в `BACKLOG.md`), и до тех пор чарт этого не обещает.

## Обновление и откат

Измерено, а не выведено из кода (стенд: k0s, один узел, образы из GHCR против сборки из `main`):

| направление | что происходит |
|---|---|
| стор от старой версии открывает новая | **работает**: журнал читается целиком, `stopped by CLEAN`, объекты на месте |
| стор от новой версии открывает старая | **отказ старта**, и журнал остаётся **байт в байт** прежним |

**Откат назад по версиям — это не «потеряете новые возможности», это «сервер не поднимется».**
Хватает одного пустого бакета: запись о его создании с версии `v0.2.0` несёт владельца, а это тип
записи, которого прежние версии не знают. Ни ACL, ни версионирование, ни объекты для этого
не нужны.

Хорошая половина: **отказ безопасен**. Исключение вылетает из восстановления **до** усечения
журнала по последней целой записи, поэтому неоткрытый стор остаётся ровно таким, каким был, и
открывается обратно новой версией. Проверено сравнением размера и `sha256` файла журнала до
и после неудачной попытки.

**И одна ловушка оркестратора, которая дороже самой ошибки.** Под, который не может стартовать,
блокирует обновление `StatefulSet`: `helm upgrade` обратно на рабочий образ меняет спецификацию,
но контроллер ждёт готовности пода, который готовым не станет. Под остаётся на негодном образе
в `CrashLoopBackOff`, и лечится это **удалением пода руками**:

```bash
kubectl delete pod <release>-0 -n <namespace>
```

**Что при этом написано в логе, зависит от версии, которая отказалась.** Начиная с M-222 это одна
строка, объясняющая себя:

```
bochka will not start: …/index.log holds an index record of kind 99, which this version of bochka
has no case for. Its checksum verified, so the record is intact and was written by a newer version:
this is a downgrade, not damage. Nothing here has been changed — the journal is exactly as it was
found, and the version that wrote it opens this directory as before. Roll forward, or restore a
copy taken before the upgrade.
```

Утверждение «запись цела» — не вежливость: восстановление сверяет CRC32C **до** разбора, поэтому
испорченный байт останавливает чтение как рваный хвост, а не как неизвестный тип. Дошло до
разбора — значит записано целиком и тем, кто этот тип знал.

Версии до этого отвечают `IllegalArgumentException: unknown index record kind N` и стеком, а
`kubectl logs --tail` показывает хвост этого стека, где причины нет. Там смотреть надо весь лог
падения, а не последние строки.

**Одно поле здесь опаснее всех остальных вместе.** `lifecycleDaySeconds` — это длительность
«суток» для правил жизненного цикла, и всё, кроме `86400`, удаляет данные раньше срока ровно
во столько же раз: правило `Expiration: Days: 1` при `lifecycleDaySeconds: 5` сносит объект через
пять секунд. Поле существует по одной причине — чужой сьют меряет истечение **ожиданием**, поэтому
оценить развёрнутый сервер на этой семье иначе нельзя (M-218), — и любое другое значение чарт
отвергает, пока `lifecycleDayShortenedFor` не назовёт причину. Период обхода следует за этим
значением, а не задаётся рядом: сервер выводит его как десятую часть «суток».

**Чего чарт не делает.** Списком, потому что каждый пункт — это ручка, которую в чужих чартах
ожидают увидеть:

* **нет `replicaCount`** — даже равного единице. Реплики у этого сервера не «пока не сделаны»:
  каталог данных не защищён ни `FileLock`, ни файлом блокировки, два процесса над одним каталогом
  дописывают журнал друг за другом, уплотнение одного переносит новый журнал поверх старого через
  `ATOMIC_MOVE`, после чего второй пишет в удалённый инод, а сбор сирот каждого удаляет файлы,
  на которые указывает индекс другого. Ручка «сколько реплик» — это обещание горизонтального роста
  от сервера, который держит один диск. Отсюда же `StatefulSet` вместо `Deployment` и отсутствие
  `PodDisruptionBudget`: у однорепличного хранилища `minAvailable: 1` просто вешает drain узла,
  а честного «без простоя» здесь нет;
* **нет `service.type`** — только `ClusterIP`. Порт 9000 говорит открытым HTTP, и `LoadBalancer`
  одной строкой отменил бы то же самое, ради чего в `docker run` выше стоит `-p 127.0.0.1:9000:9000`;
* **нет `JAVA_OPTS` и вообще любых `BOCHKA_*` в `extraEnv`.** Профиль рантайма запечён в дистрибутив,
  и от него выведен объявленный потолок объектов; неизвестное имя на `BOCHKA_*` останавливает
  процесс с кодом 2, известное — молча перебивает то, что чарт уже отрендерил из values. Двух имён
  этот запрет касается особо: `JAVA_OPTS` и `BOCHKA_APP_OPTS` читает стартовый скрипт, а не сервер,
  и оба меняют кучу молча — второе с тех пор, как перестало быть отказом (M-142). По той же
  причине отвергается `limits.memory` ниже 768Mi. Число измерено, а не сложено (M-148): при индексе
  на опубликованном потолке, четырёх клиентах, листингующих его рекурсивно, и пробе `exec` в том же
  cgroup **576Mi живёт, 512Mi получает OOM-kill**. 768Mi — это измеренный пол плюс треть, и запас
  оставлен сознательно: пол, измеренный под одной формой нагрузки, — это пол одной формы нагрузки;
* **нет `Ingress` без TLS.** Не «не рекомендуется» — не рендерится.

**Чего не видит проба живости, прямым текстом.** Ручки здоровья в сервере нет: единственный ответ
без учётных данных — `403` на `GET /`, а `httpGet` у kubelet считает успехом только 200–399. Поэтому
проба — `exec`: `bash` открывает `/dev/tcp`, шлёт `GET /` и ждёт в первой строке ` 403 `. Она
доказывает, что сервер принял соединение, разобрал запрос, прошёл проверку подписи и ответил.

С выпуском, который несёт `GET /-/healthy` (M-143), это становится `probes.type: http` — тот же
объём доказательства, но без форка шелла каждый период; умолчание переедет вместе с `appVersion`.
Что она **не** доказывает, от формы не зависит — ни `exec`, ни `httpGet` не знают ничего про
хранилище:

* зависший диск — та же `403`;
* залипший лок писателя — та же `403`;
* полный том — та же `403`;
* дошедший потолок объектов — та же `403`, и это самый неприятный случай: `PUT` каждого нового ключа
  отвечает `507` навсегда, перезапись, чтение и удаление работают, под остаётся `Ready`, рестарта
  нет и в логе пусто. `kubectl get pods` в этом состоянии показывает исправное хранилище.

Ждать от `livenessProbe` перезапуска в этих случаях не надо: она их не различает, а перезапуск
одноузлового стора и не починил бы ни один из них.

**Что будет с данными, когда релиз удалят.** Том остаётся. Он заявлен `volumeClaimTemplate`, то есть
создан контроллером `StatefulSet`, а не Helm: у Helm нет о нём записи, `whenDeleted` и `whenScaled`
стоят на `Retain`, и `helm uninstall` его не трогает. Удаление данных — отдельная и сознательная
команда:

```bash
kubectl -n <namespace> delete pvc data-<release>-0
```

Обратная сторона: `helm install` в тот же namespace с тем же именем релиза **подхватит старый том**
со всеми объектами. Это чаще то, чего хотят, но узнавать об этом лучше не по содержимому листинга.
Единственная форма, которая теряет данные молча, — `persistence.enabled: false`: тогда
`/var/lib/bochka` это `emptyDir`, и объекты живут до пересоздания пода — до обновления, вытеснения
или drain узла, — исчезая без ошибки и без строчки в логе.

Ещё одно следствие относится и к запуску без Kubernetes: **выбор диска здесь не косметика.** Каждый
`PUT` стоит двух барьеров — файл объекта с `force(true)`, затем запись индекса с `log.force()`, —
потому что `Durability.FSYNC` включён всегда и наружу не настраивается. Сетевой том платит за это
на каждой записи.

**Где здесь TLS.** Там же, где и в схеме с nginx выше, и по той же причине (§1.7 ресёрча): снаружи
процесса. Внутри пода терминатора нет, `Service` — `ClusterIP`, то есть по кластерной сети ездит
открытый HTTP, и это осознанно — ровно как `-p 127.0.0.1:9000:9000` в `docker run`. Наружу это
выставляют двумя способами:

* `ingress.enabled: true` с обязательным `ingress.tls` — чарт отказывается рендерить `Ingress` без
  сертификата, потому что подписанный запрос без TLS едет открытым текстом вместе с подписанным
  `Host` и всеми покрытыми заголовками. Умолчания аннотаций рассчитаны на ingress-nginx и повторяют
  четыре требования из [`nginx/nginx.conf`](nginx/nginx.conf): размер тела, буферизация запроса,
  буферизация ответа, таймауты. На другом контроллере они инертны, и нужны его собственные —
  чарт поэтому не рендерится, пока оператор не назовёт свой контроллер в
  `ingress.requirementsExpressedFor`;
* либо свой терминатор, нацеленный на тот же селектор, — если он уже есть, `Ingress` не нужен вовсе.

Чего эта схема **не** даёт по сравнению с nginx на одной машине: `BOCHKA_ACCEL_REDIRECT` в чарте нет
и как поля values не будет. Он осмыслен только тогда, когда терминатор читает тот же каталог данных
— тот же том, тот же узел, — а `Ingress` стоит в другом поде и, как правило, на другом узле.
Включённый вслепую, он отдаёт на чтение целого объекта `200` с пустым телом и заголовком
`X-Accel-Redirect`, что выглядит как потеря данных.

**Проброс `Expect: 100-continue` проверен на двух контроллерах, и они ведут себя по-разному.**
bochka отвечает `100 Continue` сама, и прокси, съевший заголовок, отменяет не загрузку, а её ранний
отказ — то есть превращает бесплатный `403` в `403` ценой всего тела. Замерено одним и тем же
запросом (`PUT` с телом, подписью верной формы и неверного значения) прямо в `Service` и через
контроллер: **ноль байт тела до отказа** на ingress-nginx v1.15.1 (M-144) и ноль на Traefik v3.6.0
(M-213) — **но на Traefik только пока объявленное тело больше 256 КиБ**. Ниже этой границы ответ
до клиента не доезжает вовсе, и клиент виснет до собственного таймаута; разбор и числа —
в [docs/measurements.md](../docs/measurements.md).

**Про Traefik стоит знать две вещи, и ни одна не в аннотациях.**

Три требования из четырёх он выполняет умолчаниями: буферизация выключена в обе стороны, потолка
тела нет. Четвёртое, длинный таймаут чтения, **из `Ingress` не выражается ни у кого** —
`entryPoints.<имя>.transport.respondingTimeouts.readTimeout` живёт в статической конфигурации
Traefik и по умолчанию равен 60 секундам. Аплоад, идущий дольше минуты, обрывается посреди тела:
без `413`, без `504`, просто закрытым соединением. Порог зависит от скорости клиента, а не от
размера — на 2 МиБ/с это около 120 МиБ. Ставится нулём на том entryPoint, который обслуживает
этот `Ingress` (M-211).

Вторая настройки не имеет. **Ответ, который bochka выдаёт до чтения тела — любой отказ по подписи,
по ACL или из-за отсутствующего бакета, — за Go-прокси не доезжает до клиента, ждущего
`100 Continue`, если объявленное тело не больше 256 КиБ.** Закончив обработчик, сервер Go дочитывает
остаток тела ради переиспользования соединения; клиент ждёт `100 Continue`, которого не будет, и обе
стороны стоят до клиентского таймаута. Граница ровно `maxPostHandlerReadBytes = 256 << 10`. Шесть
кейсов `ceph/s3-tests` падают на этом, и все — с телом в несколько байт. Это цена жизни за прокси
на Go; ingress-nginx на C так себя не ведёт (M-213).

И то же самое с другой стороны: **пользовательские метаданные возвращаются с изменённым регистром
имени.** Go канонизирует имена заголовков, `botocore` снимает префикс `x-amz-meta-` и оставляет
остаток как есть, поэтому `foo` приезжает как `Foo`, а `twoWords` — как `Twowords`. Регистр не
искажается, а теряется, и клиент, ищущий свой ключ, получает `KeyError`. В bochka чинить нечего:
имя уходит из процесса в нижнем регистре.

## Чем это запускать

Образ несёт свою JRE 25 и ничего не требует. **Дистрибутив — требует:** стартовый скрипт берёт
`java` из `JAVA_HOME` или `PATH`, а собран он под байткод JVM 25, так что на машине с более старой
Java падает так:

```
UnsupportedClassVersionError: ... class file version 69.0, this version of the
Java Runtime only recognizes class file versions up to 61.0
```

Читается как поломка сборки, а это поломка запуска. Поймано на раннере GitHub, где `java` по
умолчанию 17; на своей машине этого не видно ровно до тех пор, пока там стоит 25.

## Настройки

Их список — единственный, и он живёт в
[`Configuration.Key`](../bochka-app/src/main/kotlin/io/github/youndie/bochka/app/Configuration.kt).
Имя пишется `data.dir` в файле (`BOCHKA_CONFIG`) и `BOCHKA_DATA_DIR` в окружении; окружение
выигрывает.

**Неизвестное имя останавливает процесс.** `BOCHKA_DATADIR` вместо `BOCHKA_DATA_DIR` — это объекты
во временном каталоге и сервер, который об этом молчит; поэтому он не молчит, а отказывается
стартовать, называет опечатку и подсказывает ближайшее настоящее имя. Цена честная и стоит того,
чтобы её назвать: переменная `BOCHKA_*`, заведённая в окружении для чего-то другого, этот сервер
остановит.

## Сколько объектов поместится

Столько, сколько поместится в кучу: индекс держит все ключи (Р1). Умолчание поставки — `-Xmx512M`,
то есть **399 215 объектов** при 650 байтах индекса на объект. Число печатается первой строкой лога
как `object ceiling`, и считается оно от `Runtime.maxMemory()`, а не от `-Xmx`: под `SerialGC` куча
в 512 МиБ отчитывается как 494.9 МиБ, потому что один survivor-space в неё не входит.

**И потому это число — про сборщик, а не только про кучу.** `maxMemory()` каждый сборщик
отчитывает по-своему: при одном и том же `-Xmx512M` — 455 МиБ под ParallelGC, 494 под SerialGC,
512 под G1, то есть потолок 367 404, 399 215 или 412 977 (замер — `docs/measurements.md`, M-152).
Поэтому вторая строка лога называет сборщик: обёртка, подменившая его, двигает опубликованное
число, не тронув ни строчки документации. Больше — больше куча:

```bash
-e JAVA_OPTS=-Xmx3G  # нет; см. ниже — работает, и именно поэтому нельзя
```

Профиль задаётся при сборке дистрибутива — и **перебивается** `JAVA_OPTS`. Здесь стояло обратное
утверждение, и оно было неверным: стартовый скрипт, сгенерированный Gradle, склеивает
`$DEFAULT_JVM_OPTS $JAVA_OPTS $BOCHKA_APP_OPTS` в этом порядке, а HotSpot берёт **последний**
`-Xmx`. Замерено смоук-тестом: под `-e JAVA_OPTS=-Xmx3G` процесс печатает `object ceiling: 2395290`
вместо 399 215, причём `-Xmx512M` остаётся в `/proc/1/cmdline` — то есть проверка «в командной
строке есть -Xmx512M» проходит и означает не то, что читается.

Следствие для того, кто заворачивает этот образ в свой чарт или compose: **ручку `JAVA_OPTS`
наружу выставлять нельзя**. Не «не рекомендуется» — от неё зависит опубликованный потолок объектов,
и подменённая куча делает напечатанное число числом про процесс, которого никто не запускал. Чарт
поэтому запрещает `JAVA_OPTS` и любые `BOCHKA_*` в `extraEnv`, а смоук-тест проверяет **эффект** —
напечатанный потолок под тремя окружениями, — а не наличие подстроки. Чтобы поднять потолок честно,
пересоберите дистрибутив с `-Pbochka.jvmArgs`.

Достигнутый потолок — это **`507 InsufficientStorage` на `PUT` каждого нового ключа**
(`ObjectStore.kt:574`), и навсегда: условие само не изменится. Перезапись существующих ключей,
чтение, удаление и листинг при этом работают, процесс жив и в лог об этом ничего не пишет. Отказ
при старте (`ObjectStore.kt:289`) — другой случай: он срабатывает, когда индекс **уже** больше
потолка, то есть потолок опустили под него (меньший `BOCHKA_MAX_OBJECTS` или меньшая куча). При
обычной работе индекс выше потолка не вырастает, потому что записи отклонены раньше. Ни в том, ни
в другом случае деградации в своп нет, и это было целью: процесс, который поднялся и начал
свопиться, выглядит как медленный диск для всех, кто не писал индекс.

## Обслуживание

Раз в час (`BOCHKA_HOUSEKEEPING_MINUTES`) сервер уплотняет журнал индекса, собирает файлы-сироты
и забывает брошенные многочастные загрузки. Уплотнение — не про место на диске: восстановление
пропорционально журналу, и полмиллиона объектов в трёх поколениях открываются 3.5 с против 0.76 с
после уплотнения.

Проверено под нагрузкой, а не только на синтетике: за сто часов и миллион записей журнал ни разу
не вышел за 2.4 МиБ, уплотнение не вызывалось руками ни разу, а восстановление после перезапуска
осталось неотличимым от пустого каталога — меньше 0.9 с на старт JVM и чтение журнала, 5.3 с на
перезапуск целиком, как его видит клиент.

## Память: контейнер всегда выглядит полным, и это норма

Замерено соаком в сто часов ([docs/measurements.md](../docs/measurements.md)): под нагрузкой
`memory.current` стоит **на лимите** — 767 МиБ из 768, — и держится там сутками. Убийства при этом
нет ни одного: за сто часов ядро вытеснило кэш семьдесят одну тысячу раз.

Лимит забит не процессом:

```
anon   520 МиБ   процесс — куча, метаспейс, код, стеки
file   144 МиБ   вытесняемый страничный кэш файлов объектов
slab    65 МиБ
```

Тот же образ на простаивающем стенде — 143 МиБ всего. То есть полный лимит это свойство трафика.

**Алерт на память стройте по `workingSetBytes` или по `anon`, но не по `usage`** — иначе он будет
срабатывать вечно на исправном сервере. И заранее: `kubectl top` покажет 178 МиБ там, где
`memory.current` показывает 767. Оба правы, первый вычитает вытесняемый кэш.

### Сколько остаётся на горячие файлы

Куча и страничный кэш берут из одного лимита. За сто часов JVM закоммитила 448 МиБ из своих 512,
чтобы держать девять мебибайт живых данных, — и кэш отдал ровно столько же, с 605 МиБ до 144.
Дефекта тут нет: `-Xmx512M` куплен под полный индекс (399 215 объектов × 650 байт ≈ 260 МиБ).
Но путь чтения — `transferTo` из **горячего** файла, поэтому размен настоящий: **куча покупает
потолок по числу объектов, кэш покупает скорость чтения.**

На умолчаниях под горячие файлы остаётся **порядка 115–145 МиБ**. Если ваш горячий набор больше:

* **поднимите `limits.memory`** — `-Xmx` ограничивает JVM сверху, поэтому весь избыток достаётся
  кэшу. Лимит в 2Gi даёт около 1.4 ГиБ под файлы, пересобирать ничего не надо;
* **уменьшите `-Xmx`**, если объектов заведомо немного, — но это пересборка дистрибутива
  (`-Pbochka.jvmArgs`), и потолок по числу объектов упадёт пропорционально: 650 байт на объект,
  половина кучи;
* `BOCHKA_ACCEL_REDIRECT` выше — отдачу берёт на себя nginx, и цена у него своя.

## Проверка здоровья

```
curl -sf -o /dev/null -w '%{http_code}' http://127.0.0.1:9000/   # ждём 403
```

Именно запрос, а не открытие сокета: TCP-соединение устанавливается и с JVM, которая застряла
в сборке мусора и не отвечает ничего. `403` здесь — правильный ответ: запрос без учётных данных
корректен и просто ничей.
