# Спецификация в репозитории

У S3 нет RFC. Здесь лежат ближайшие к спецификации артефакты, которые можно положить в репозиторий
и читать без сети. **Ссылка отсюда обязательна в каждом тесте** — правило 2 проекта: тест,
написанный «по здравому смыслу», не принимается.

Прозаическая документация AWS (`docs.aws.amazon.com/AmazonS3/latest/API/…`) сюда **не копируется**:
она отдаётся JavaScript'ом, текстовой версии нет, лицензии на редистрибуцию тоже. На неё ссылаемся
URL'ами.

## Чем это отличается от такого же набора у клиента

Файлы те же, направление обратное. Клиент подпись **строит**; bochka её **проверяет**, и разница
не косметическая:

* вектор для клиента — это «дай тот же `Authorization`». Для сервера — «прими этот запрос и отвергни
  его же с испорченной подписью»; второй половины в векторах нет, её пишем мы;
* сервер обязан понимать то, чего клиент может не уметь: `aws-chunked` с подписью каждого куска
  и трейлеры (ресёрч, §1.1). Векторов на это не публикует никто — их заменяют живые клиенты (Р6);
* у сервера появляется свой класс ошибок — «подпись не сошлась», — и в теле ответа он обязан
  вернуть **свой** canonical request, потому что иначе клиенту нечем сравнить (задача M-19).

## Что лежит

### `aws-sig-v4-test-suite/` — официальные векторы подписи

34 кейса, по пять файлов на кейс:

| Файл | Что в нём |
|---|---|
| `<case>.req` | сырой HTTP-запрос — вход |
| `<case>.creq` | ожидаемый canonical request |
| `<case>.sts` | ожидаемый string to sign |
| `<case>.authz` | ожидаемый заголовок `Authorization` |
| `<case>.sreq` | тот же запрос с подставленным заголовком |

Входные данные фиксированы для всех кейсов:

```
access key  AKIDEXAMPLE
secret key  wJalrXUtnFEMI/K7MDENG+bPxRfiCYEXAMPLEKEY
timestamp   20150830T123600Z
region      us-east-1
service     service
```

**Важно про `normalize-path/`.** Восемь кейсов из 34 проверяют нормализацию пути (`/./` → `/`,
`/example space/` → `/example%20space/`). Это поведение **общего** SigV4; S3 путь не нормализует
и не перекодирует (`reference/botocore-auth.py:538`). В S3-режиме эти кейсы обязаны давать другой
ответ.

Источник: `boto/botocore`, `tests/unit/auth/aws4_testsuite`. Лицензия — Apache 2.0, файлы `LICENSE`
и `NOTICE` лежат рядом и удалению не подлежат.

### `s3-signing-vectors/` — векторы для того, чего AWS не публикует

Официальный набор покрывает **общий** SigV4. Двух вещей в нём нет вовсе: правила S3 «путь
подписывается как есть» и presign.

| Что | Где |
|---|---|
| 13 кейсов подписи заголовками | `header/<case>/` — `input`, `creq`, `sts`, `authz`, `sha256` |
| 7 presign-ссылок | `presign/<case>/` — `input`, `url` |
| Кодирование ключей питоновским `quote` | `key-encoding` |
| Версия botocore, которой сгенерировано | `generated-with.txt` (сейчас `botocore 1.43.72`) |

Генератор — `s3-signing-vectors/generate.py`, лежит рядом.

**Это не официальные векторы**, и надёжны они ровно настолько, насколько надёжна эталонная
реализация. Ценность в другом: botocore — независимая реализация, а не пересказ поведения bochka.

### `key-order/` — порядок листинга

| Что | Где |
|---|---|
| 534 ключа в том порядке, в котором их возвращает `ListObjectsV2` | `key-order/vectors.txt`, hex, по ключу на строку |
| Чем порядок получен | `key-order/generate.py` — Python, `sorted()` над `bytes` |

Правило — `s3-service-2.json`, `ListObjectsV2`, раздел «Sorting order of returned objects»:
«returns objects in lexicographical order based on their key names». Для байтовой строки это
беззнаковый порядок байтов, и на JVM **оба** очевидных способа его получить неверны: `String`
сравнивается по кодовым единицам UTF-16, а `Byte` знаковый.

Ключи подобраны так, чтобы ловить оба промаха и ещё несколько: `U+FF01` против `U+1F600`
(расходятся UTF-16 и UTF-8), байты выше `0x7F` (знаковое сравнение уносит их в начало), невалидный
UTF-8, `café.txt` в NFC и NFD, `Photo.JPG` против `photo.jpg`, префиксные пары (`a`, `ab`, `a/`,
`a/b`, `a0`). Потребитель — `ObjectKeyOrderTest`.

Перегенерировать (вывод коммитится, тест Python не запускает):

```bash
python3 docs/spec/key-order/generate.py
```

Сид фиксирован, поэтому изменившийся `vectors.txt` означает, что изменился генератор, — такой дифф
надо читать, а не принимать.

### `aws-chunked/` — кадры потоковой загрузки

Единственная часть входного пути, на которую **никто** не публикует векторов, — и одновременно та,
где ошибка означает, что `aws s3 cp` не работает вовсе. Поэтому фикстуры порождены здесь, на другом
языке, по двум источникам: раскладка кадров и цепочка подписей — из эталонного сервера
(`minio/minio`, `cmd/streaming-signature-v4.go`), беззнаковая форма — из botocore
(`httpchecksum.py`, `AwsChunkedWrapper`).

| Кейс | Что проверяет |
|---|---|
| `signed-one-chunk`, `signed-several-chunks` | базовая цепочка |
| `signed-64k-chunks` | размер куска, которым шлют SDK, — 64 КиБ |
| `signed-empty-object` | нулевой объект: остаётся только финальный кадр |
| `signed-trailer-crc32` | подписанный трейлер и контрольная сумма |
| `unsigned-trailer-crc32` | то, что современные SDK шлют по умолчанию |

В каждом каталоге: `body` (байты на проводе), `object` (что должно получиться), `meta`
(ключ, секрет, метка времени, seed-подпись, длина, объявленные трейлеры).

Две вещи, которые видно только отсюда и обе стоят падения:

* **Строки подписи разной длины.** У куска — пять строк (`AWS4-HMAC-SHA256-PAYLOAD`, метка, scope,
  предыдущая подпись, sha256 пустой строки, sha256 куска), у трейлера — четыре
  (`AWS4-HMAC-SHA256-TRAILER`, метка, scope, предыдущая подпись, sha256 трейлера): строки про
  пустое тело в трейлере **нет**. Ошибка проявляется на самом последнем кадре загрузки, которая
  до этого шла идеально.
* **У финального нулевого кадра нет своего CRLF.** У кадра с данными после тела идёт `\r\n`,
  у нулевого — сразу трейлер либо пустая строка конца тела. Первый генератор ставил там лишний
  перевод строки, и это поймал декодер.

```bash
python3 docs/spec/aws-chunked/generate.py
```

### `checksums/` — что клиент утверждает о теле

| Что | Где |
|---|---|
| векторы для `Content-MD5` и `x-amz-checksum-*` | `checksums/vectors.txt`, по строке `имя ⇥ алгоритм ⇥ base64` |
| чем получены | `checksums/generate.py` — Python, `hashlib` и `zlib` |

Алгоритмы: `crc32`, `crc32c`, `crc64nvme`, `sha1`, `sha256`. Первый и последние два берутся из
стандартной библиотеки Python; **CRC32C и CRC-64/NVME реализованы в генераторе от полинома** —
их в stdlib нет, и это независимая реализация той же спецификации, а не перевод здешней.

CRC можно ошибиться четырьмя способами так, что получатся правдоподобные байты: полином, его
запись (прямая или обратная), направление сдвига, начальное и конечное исключающее ИЛИ. Поэтому
в наборе есть кейс `check-123456789` — вход, для которого каталог публикует **проверочное
значение**; для CRC-64/NVME это `0xAE8B14860A799888`, и генератор падает, если не сходится.

Отдельная грабля этого набора: `crc64nvme` попал сюда не из полноты. Он был отвергнут по имени
как «редкий», и первый же `aws s3 cp` ответил `NotImplemented` — `aws-cli` v2 ставит этот
заголовок на **каждую** загрузку по умолчанию. Список алгоритмов задают клиенты, а не вкус.

### `s3-service-2.json` — машинная модель API S3

`botocore/data/s3/2006-03-01/service-2.json`, протокол `rest-xml`. Отвечает на вопросы «какой метод
и URI у операции», «как называется query-параметр», «приезжает поле заголовком или в теле», «какой
код успеха». Единственный источник, где это записано формально, а не прозой. Всего 116 операций;
объём v1 — четырнадцать из них.

Точки входа по строкам:

| Операция | Строка |
|---|---|
| `AbortMultipartUpload` | `:18` |
| `CompleteMultipartUpload` | `:32` |
| `CreateMultipartUpload` | `:108` |
| `DeleteObject` | `:329` |
| `GetObject` | `:717` |
| `HeadObject` | `:878` |
| `ListObjectsV2` | `:1014` |
| `PutObject` | `:1353` |
| `UploadPart` | `:1596` |

Операции уровня бакета (`CreateBucket` — `PUT /{Bucket}`, `DeleteBucket` — `DELETE`, успех 204,
`HeadBucket`, `ListBuckets` — `GET /`, `GetBucketLocation` — `GET /{Bucket}?location`,
`DeleteObjects` — `POST /{Bucket}?delete`) ищутся по имени в `operations`.

Формы данных — в `shapes` того же файла (`ListObjectsV2Request`, `ListObjectsV2Output`,
`UploadPartOutput`, …). На них ссылаемся **путём внутри JSON** (`shapes.ListObjectsV2Output.members`),
а не номером строки: строки в `shapes` едут при каждом обновлении модели.

**Чего в модели нет, а нам нужно:** минимальный размер части (5 МиБ), потолок длины ключа
(1024 байта), максимальный размер объекта. Всё это живёт прозой в документации AWS, и его место —
таблица в `docs/api/protocol-s3.md` с указанием, откуда взято.

## Как обновлять

Все артефакты — снимки, а не подписки. Обновляются руками и **отдельным коммитом**, потому что
после обновления номера строк в ссылках из тестов и документов разъезжаются.

```bash
curl -sL -o docs/spec/s3-service-2.json \
  https://raw.githubusercontent.com/boto/botocore/develop/botocore/data/s3/2006-03-01/service-2.json
curl -sL -o docs/spec/reference/botocore-auth.py \
  https://raw.githubusercontent.com/boto/botocore/develop/botocore/auth.py
```

После обновления — прогнать тесты и перепроверить таблицы строк в этом файле.

Набор векторов подписи трогать не нужно вовсе: он привязан к алгоритму, а не к сервису, и его
`NOTICE` датирован 2019 годом.
